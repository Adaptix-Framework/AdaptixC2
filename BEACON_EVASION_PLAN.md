# Beacon Evasion Plan

Guiding principle: **the beacon must be invisible at runtime**. Anything that can live in the loader or an inline command plugin does NOT belong here. The beacon binary stays minimal — every byte of added code is attack surface for static signatures and memory scanners.

---

## DONE

- [x] **Sleep obfuscation (Ekko)** — beacon memory encrypted with RC4 (SystemFunction032) during sleep via timer-queue ROP chain. x64 only; x86 falls back to plain sleep. Preserves BOF wake via event handle.
- [x] **Default fingerprint removal** — server header (`nginx`), 404 page (stock nginx), heartbeat header (`X-Request-ID`), URIs, User-Agents (Chrome 125), ports (8443), TCP banner (empty), error answers (empty), pipe names, payload template, sleep (1m30s), jitter (25%), service name (`WinUpdateSvc`).

---

## SPRINT 1 — Syscall hardening (runtime API calls)

Every ntdll call the beacon makes while alive is hookable. This is pure runtime — cannot be offloaded to loader.

- [x] **SysWhispers3-style SSN resolution**
  - Sort all `Zw*` exports from ntdll by address to derive correct SSN ordering
  - Works even when all stubs are hooked (address order is immutable)
  - Store resolved SSNs in a compact table at init, not per-call
  - Only resolve SSNs for functions the beacon actually uses (NtClose, NtWaitForSingleObject, NtCreateFile, NtWriteFile, NtProtectVirtualMemory, etc.)

- [x] **Indirect syscall execution**
  - Find a `syscall; ret` gadget inside ntdll's `.text` section (scan for `0F 05 C3`)
  - Route all NT calls through that gadget so the return address is inside ntdll, not inside beacon memory
  - This defeats user-mode hooks AND makes the call stack look legitimate to kernel callbacks

- [x] **Replace direct ntdll calls in existing code**
  - Audit every `ApiNt->Nt*()` call site and route through the indirect syscall path
  - Includes: Ekko sleep (NtWaitForSingleObject, NtContinue), pipe comms, file I/O
  - Keep `ApiNt` struct for non-syscall ntdll exports (RtlCaptureContext, etc.)

## SPRINT 2 — Call stack hygiene

EDR kernel callbacks (PsSetCreateThreadNotifyRoutine, ETW thread-start events) inspect the call stack. A thread whose stack frames all point into a single private RWX region is an instant detection.

- [x] **Return address spoofing on API calls**
  - Before each Win32/NT call, push a fake return address pointing into a legitimate loaded DLL (e.g., kernel32, ntdll)
  - Restore real return address after the call returns
  - Only needed for calls that may trigger kernel callbacks (thread creation, memory protection changes, process/token operations)
  - Use a JMP-based trampoline, not CALL, to avoid pushing the real return address

- [x] **Thread stack spoofing during sleep**
  - Before Ekko encrypts the image, overwrite the sleeping thread's stack frames with plausible return addresses (walking kernel32 → ntdll → KiUserCallbackDispatcher)
  - Restore after decrypt
  - This complements Ekko — encrypted image is invisible, but the thread's stack is still scannable by ETW stack walks

## SPRINT 3 — Memory artifact reduction

Minimize what a memory scanner sees when it dumps the process.

- [x] **Stomp PE headers after init**
  - Zero out DOS header, NT headers, section table after the beacon finishes initialization
  - Prevents `pe-sieve` / `moneta` from identifying the region as a PE
  - Must happen AFTER ApiLoader resolves everything it needs from the beacon's own PE

- [x] **Avoid RWX memory**
  - Ekko currently restores to `PAGE_EXECUTE_READWRITE` — change to `PAGE_EXECUTE_READ`
  - The beacon's data section should be separate and stay RW
  - Any page that is simultaneously W+X is flagged by every modern scanner

- [x] **Heap encryption**
  - Encrypt heap allocations (agent config, session key, command buffers) during sleep alongside the image encryption
  - Prevents string scanning of heap for IOCs (URLs, pipe names, keys)
  - Track allocations in a simple linked list; encrypt/decrypt in the Ekko pre/post chain

## SPRINT 4 — Telemetry blinding (in-process only)

These disable detection sources from within the beacon's own process. Loading-time patches (AMSI, ETW at DLL load) belong in the loader.

- [x] **Patch EtwEventWrite in-process**
  - Overwrite the function entry with `ret` to silence ETW events generated by the beacon's own activity (e.g., .NET assembly loads via `execute-assembly`, WMI queries)
  - Only patch when needed (before a BOF/assembly runs), restore after
  - This is runtime, not load-time — it must live in the beacon

- [x] **Unhook ntdll selectively (runtime refresh)**
  - When the beacon detects a hook on a critical function (compare first bytes against clean `mov r10, rcx; mov eax, SSN` pattern), remap just that stub from `\KnownDlls\ntdll.dll`
  - Do NOT remap the entire ntdll (noisy, triggers page-fault telemetry)
  - Only if indirect syscalls alone aren't sufficient (some EDR patches deeper than the stub)

---

## OUT OF SCOPE (loader / plugin territory)

These are important but do NOT belong in the beacon binary:

- AMSI bypass at load time
- Module stomping / reflective loading strategy
- Process injection techniques
- Shellcode encoding / packing / crypter
- Persistence mechanisms
- Privilege escalation
- Full ntdll unhooking at load time
- Anti-sandbox / anti-debug checks (debatable — keep out unless beacon needs self-protection)

## Build / compile notes

- The Makefile auto-includes all `beacon/*.cpp` via wildcard — new files just need to exist
- x86 gets fallback paths for anything that requires x64 CONTEXT manipulation
- All new API dependencies must go through `ApiDefines.h` (DJB2 hash) → `ApiLoader.cpp` (resolve) → `ApiLoader.h` (struct member)
- No CRT string literals for API names — everything is hash-resolved
- Test both x64 and x86 builds after every sprint
